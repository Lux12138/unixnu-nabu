# nabu 项目工作规则（每一轮上板前必读）

本文件是**硬闸门**，不是建议。`tmp/flash_nobootflash.sh` 会检查 `state/precheck.json` 是否新鲜；
没有通过的预检，刷写会被拒绝。

## 0. 最重要的一条

**日志优先于实验。**
每一轮之前先回答一句：**"现有日志能不能回答这个问题？"**

- 能 → **不许上板**，花这七分钟把日志读完。
- 只有日志对这个问题是沉默的，才允许开一轮。

## 0.5 静态分析红线（2026-11-05 用户拍板，优先级同 0）

**必须先把静态分析和反汇编做足、把整套传导链讲清楚，才允许上板做实验。**
仅仅为了拿某一个参数（尤其是单个参数），除非**非常必要**，一律不允许上板。

具体闸门（`tmp/precheck.py` 强制要求填这两栏）：

1. **`--chain`**：从"原因"到"板上可观测量"的完整链路，每一环都要带静态证据
   （file:line / 指令地址 / 字符串 vaddr / 符号是否存在）。写不出闭环 ⇒ 不许上板。
2. **`--why-board`**：为什么这件事**只能在板上**得到，静态方法为什么不够（例如"寄存器值只有运行期才有"）。
   填不出正当理由 ⇒ 不许上板。

反面例子（都踩过）：
- 为了看"多核有没有起来"就去传 `cpus=8`——而 step/fail 的唯一消费者 `package/BootProgress.c` 根本没编进核
  （`XNU_BOOT_PROGRESS=0`、归档无 `BootProgress.o`）⇒ 板上根本没有这个读数，属于"为了一个不存在的量上板"。
- 为了试 `sheng-smp=1` 能不能开副核——而 `ArmCpu::probe()` 的门、`startCPU()` 的 PSCI 路径、
  是否编进核都可以离线核完（已核：代码=上游+27 行 timer 修正、门在上游也有、ArmCpu 已编入）。
- 触摸固件写不进去时反复换分块/延时——而厂商 `nvt_update_firmware` 的目标地址表可以离线反出来。

**允许上板的典型正当理由**：需要寄存器/时序的**运行期**取值；需要验证"静态结论在真机上是否成立"的那**一次**判定；
日志与静态都无法产生的**新状态**（例如某个开关首次生效时的行为）。

## 0.6 双审计一致（2026-11-05 用户拍板）

**我负责审计下游交上来的成果；两边的审计结论必须完全一样，才允许上板。**

- 下游给的自检项（kernel/payload/ADT/boot 的 sha256 与大小、args 字符数、绑定条数、ADT 节点与属性计数、
  关键字符串计数、`POST_LINK_BINDINGS_PASS` 之类）我逐项**自己复测**；
- 用 `tmp/audit_dual.py --tag <tag> --peer "<下游的值>" --mine "<我实测的值>"` 比对；
  **任何一项不等、或某一侧缺项 ⇒ 不生成审计戳 ⇒ `precheck_check.py` 拒绝刷写**；
- 审计戳是 `state/audit-<tag>.json`（含 `equal:true` + 逐项值 + 时间戳），有效期与预检戳相同（40 分钟）。

审计不一致时的正确动作：**先停下来对账**（把我实测的原文、测量方法、取值时刻给对方），
不要"以某一方为准"直接上板；对不上就当作这一包不存在。

### 0.6.1 白名单审计不够——必须逐 token diff（2026-11-05 l588 事故后补）

l588 的 args 里混进了裸 `kernel_args`（构建侧正则把 TOML 键名当成了 token），而双方的双审计都只比
"字符数/白名单字段"，**两边一起错**，包照样上了板。
⇒ 每包上板前还要跑 `tmp/audit_args.py <上一包> <本包> --expect-added … --expect-dropped …`：
逐 token diff、拒重复、拒含空白/引号/`kernel_args`，增删集合必须与声明完全一致。
`tmp/precheck.py --pkg <本包> --baseline <上一包> …` 会**自动**跑它，不通过就不写预检戳。

## 0.7 看门狗必须与 panic 时刻相容（2026-11-05 l588 事故后补）

`nabu-wdt-arm-delay=N` 是**第 N 秒才武装**看门狗。早期 panic（SMP 轮实测 t≈30 s）若发生在武装之前，
狗永远不会来，板子挂死、只能人工断电——l588 就是这样卡住的。

- **凡是带 `sheng-smp=1` 的轮次，一律 `arm-delay=0`**（`precheck.py` 已硬性拒绝 `sheng-smp=1 + arm>0`）；
- 其它可能出现早 panic 的开关同理：先问"panic 会不会早于 N 秒"，会就写 0；
- 窗口预算随之变化：`arm=0` 咬点实测 ≈380–410 s（不是 471 s）。

## 0.8 禁止 sleep（用户已多次点名）

不许 `sleep N; 看结果`、`read -t`、`tail -f | grep -m1`、`while ! grep` 这类阻塞等待。
要等就：后台任务 + 完成通知，或 10 秒轮询且每轮打印状态（时间/状态/剩余）。

判据在哪找（按优先级）：

| 想知道 | 去哪里看 |
|---|---|
| 系统走到哪一步 / 谁被拉起 / 谁死了 | `logs/cdc-*.bin` 的 `spawn>`、`exec done`、`process exit` 行（按 `t=` 排序） |
| 屏幕上是什么 | `logs/rounds/*.json` 的 `state_line`（`gop_p0/bb/po/nswap/fbcon`） |
| 某轮完整时间线 | `logs/*-ring.txt` 的 `NABUSTATE1` |
| 某个开关生没生效 | 环里的 `NABUFB*`/`NABUAKS*`/`NABU TOUCH` 等自身标记行 |

已踩过的坑（都用日志能避开）：
- 用"画面没变"推"功能丢了"——实际是 `PreBoard` 压根没被拉起（`t=363` 那一行就在日志里）。
- 用累计 `spawn` 数比较两轮——必须先裁到**同一 t**。
- 用单条状态行判"到没到页"——页只活十几秒，`NABUSTATE1` 每 20 s 一条。

## 0.9 上板报告（2026-11-07 用户拍板，优先级同 0）

**每次上板前必须写 `state/board-report-<tag>.md`，缺一项即禁止刷写。**没有充分合理性说明上板意义的上板，视为违规。

报告至少回答六问：

1. **唯一问题**：这一轮只回答哪一句话？
2. **已闭合到哪**：现有日志与静态证据已经排除了什么（列环节，不是形容词）。
3. **为什么离线不行**：缺的是哪个只能运行期得到的量；写不出就说明不该上板。
4. **失败也有信息**：如果结果是否定的，会得到什么可判读的新事实？（"再看看"不算）
5. **唯一变量 + 回滚点**：与上一包逐字节相同的部分列出来；回滚到哪个包、怎么回滚。
6. **恢复预案**：早死/卡死时软件侧能不能拉回（fastboot 命令是否可用）；不能就提前写明需要人工断电。

`tmp/flash_nobootflash.sh` 会检查该文件存在且是本包的 tag，否则拒绝刷写。

## 0.10 绝对红线：不许碰 boot 分区（2026-11-07 用户拍板，优先级同 0）

这块平板**没有独立的 recovery 分区，recovery 就在 boot 里**（boot_a 里是 TWRP）。

- **任何情况下都不允许 `fastboot flash boot_a` / `fastboot flash boot`**——不写"临时启动"、不写"还原"、不做任何理由的例外。
- 启动 UniXNU 内核只用 `fastboot boot <boot-merge-r3.img>`（临时加载，不写任何分区）。
- 真正需要还原时，只由用户当场点名文件，并且仍然不经过这里的自动化脚本。
- 脚本层强制：`tmp/guard_no_boot_flash.py` 在每次刷写前扫描命令文本，出现 `flash boot` 立即 `exit 4`。
- 违反的代价（11-07 13:42 实测）：boot_a 被 Mu 镜像覆盖 ⇒ recovery 消失 + misc 被清 ⇒ 设备每 4 分钟自启一轮内核，
  只能靠人手按键才出得来；恢复要用户点名备份文件 `backup-boot_a-20261103.img`。

## 1. 每一轮必须写下的四件事

在开跑前，用 `tmp/precheck.py` 落盘（它会生成 `state/precheck.json`）：

1. **具名问题**：这一轮要回答的那一句话。
2. **日志先说**：现有日志已经给出的部分是什么（有/无/矛盾）。
3. **窗口预算**：目标现象预计在第几秒出现，`arm-delay` 设成多少。**不要手拍**，用标定式：
   `arm-delay = 目标秒数 + 余量(默认100) - 360`，咬点 ≈ arm-delay + 360
   （实测 380/450/1206 对应 arm 0/90/840）。直接跑
   `python tmp/mkround.py --base <包> --name <新名> --target <秒> --question "<问题>"`
   它会算出 arm-delay、做 args 手术、并把问题/窗口/内核哈希写进新包的 `round.json`。
4. **变量表**：内核线（KERNEL~1MAC 前 8 位）/ args（长度+关键 token）/ 设备状态 / 窗口长度，四行。

## 2. 一轮结束后

- 先判读，再决定下一轮；不允许"上一轮还没读，就排下一轮"。
- 判读结论写回 `logs/rounds/<tag>.json` 与记忆；**否定结论也要写**（避免重复试）。
- 若结论是"日志本来就能回答"，把这个问题补进上面的判据表。

## 3. 不允许的行为

- 连续两轮问同一个问题而中间没有新证据。
- 用"再跑一轮看看"代替读日志。
- 把"没采到"当成"没发生"。
